Pier 用一份 C ABI 把基岩服务端暴露出来。模组就是一个会说这份 ABI 的动态库，
所以**用什么语言写，是作者的选择，不是平台替他做的决定**。

Rust 是第一个官方绑定。Go、Zig，以及任何有 C FFI 的语言都可以有自己的绑定，
而且加一个绑定不需要动 Pier。

## Pier 为什么存在

它的前身是 [levilamina-rust-loader](https://github.com/Maskviva/levilamina-rust-loader)，
当初只为回答一个问题：LeviLamina 的模组能不能用 Rust 写？

能。而这个答案带出了一个更难的问题。那个装载器的接口是一次加一个函数长出来的，
底下的形状错了，而且错在补丁补不掉的地方：

- **布局按构建目标分岔。** 函数表里的条件编译，让它的尾部在客户端构建和服务端构建上
  落在不同的偏移。为此在版本号高位打了个标记补救，可这个标记护不住任何一个没重新编译的
  模组——分岔点之后的每一个槽位都打到了错的函数指针上，而两边都编得过。
- **中心直接呼叫每个能力包。** 派发表里写着各个包的函数名，每一个名字都是一条从中心
  伸向能力包的链接边，于是能力包根本删不掉。「可选」是文档里的一个词，不是代码的性质。
- **读不到的值，变成了看起来合理的值。** 一个读不出来的字段返回 0，而 0 对多数东西
  来说都是个合法答案。土地保护模组读不到事件里的维度，写了 `unwrap_or(0)`，于是
  每个事件都被当成发生在主世界——主世界拒绝、别处全部放行，一行日志都没有。
- **事件名做子串匹配。** 上游哪天新增一个含相同词干的事件，订阅方就会被静默劫持到
  载荷形状完全不同的合成事件上，而且没有任何办法再订到真事件。

这四条单独看都能修，也确实补过几个。但合起来它们说明的是一件补丁修不了的事：
**这个接口从来不是设计出来的，是长出来的**，而那些补丁是在守一个本就不该存在的形状。

那个装载器是测试版。测试版的作用就是告诉你该怎么正经地建，它做到了，然后就不再维护。

Pier 是重新设计：先有接口，后有实现。

## Pier 是怎么设计的

Pier 的全部就是一份头文件
[`packages/pier-abi/include/sdk/abi.h`](packages/pier-abi/include/sdk/abi.h)。
仓库里其余的一切都只是它的一个实现。这个顺序上的倒置，正是上面那四个问题
被认真对待之后的结果。

### 一份布局，通吃所有目标

`PierApi` 里没有任何条件编译。客户端专属的那组槽、自定义维度的那组槽，在每一种构建里
都占着位置，只是在对应的能力包没编进来时为 NULL。

于是「宿主有没有这个能力」变成了一个关于指针的问题，在运行期回答，同一份模组源码
在所有目标上都编得过。版本号高位的标记，以及为守住它而生的那一串补丁，全都不需要
存在了——因为布局不再分岔。

### 能力包向内注册

装载器的派发表直接呼叫各包的函数，这正是可选包删不掉的原因。Pier 把这条边反了过来。

能力包通过一套服务提供方接口（SPI）向宿主注册自己，共四个注册面：

| 注册什么 | 宿主何时用 |
|---|---|
| 槽位包 | 装载期填 `PierApi` |
| 拆除步骤（带 stage 编号） | 卸载时按 stage 升序执行 |
| 卸载否决 | 允许卸载之前逐个问 |
| 事件提供方 | 解析一次订阅时 |

包不在，注册就不发生，槽位保持 NULL，`pier-host` 一行都不用改。

**「可选」因此是可执行的**，而且就是这么定义的：把根构建文件里那一行 `includes(...)`
删掉，配置、编译、运行全部照常，对应槽位为 NULL。有一条检查逐包执行一遍这句话。

自注册有一个前提值得说明：所有包都编译成 object 而不是静态库。静态库会让链接器丢弃
没有外部符号引用的编译单元，而那些注册恰恰是**零外部引用**的文件级静态对象。被丢弃之后
的症状是功能静默消失。这一条写进了契约，也有检查守着——因为它在写进契约之后仍然被违反过一次。

### 句柄是身份，不是指针

没有任何东西以「指向服务端内部的指针」的形式跨过 ABI。玩家是一个选择器，实体是一个 id，
方块是维度加坐标。每次调用都重新解析一遍。

所以句柄可以跨 tick 留着：实体没了之后调用返回错误，而不是跳进一块已经释放的内存。
代价是每次调用多一次查表——对于一条另一侧是 Pier 管不着的代码的边界来说，这个交换是划算的。

有一条身份规则值得单独说，因为它是安全性质。按**名字**寻址的玩家选择器，在账号名匹配不上时
会退到显示名，而显示名可以被别的模组改。一个玩家把自己的显示名改成某个离线玩家的账号名，
就能让所有按名字寻址的调用落到自己身上。权限、经济、归属判定一律用 xuid，
Rust 绑定把这个区别写进了类型，让它在调用点上看得见。

### 缓冲区归产出方所有

任何跨边界的缓冲区，由产出方分配、产出方释放，接收方要留就自己拷。

| 形状 | 谁分配 | 接收方能做什么 |
|---|---|---|
| `PierStr`（指针 + 长度） | 调用方 | 返回前读完，要留自己拷 |
| Sink 回调 | 宿主 | 在 sink 内拷走，返回后指针失效 |
| 车道的 `data` / `vtable` | 提供方 | 只在存活标志为真时调用 |

ABI 上永远不会返回一个「需要对方释放」的指针。那需要一份跨边界的分配器契约，
而两边的分配器不是同一个。所有输出都走 sink。

结构化数据走 SNBT 而不是按值传递的结构体，这样一门表达不了引擎内存布局的语言也不必去表达。

### 错误就是错误

没有任何一个槽位会用一个看起来合理的值，去回答一个它其实答不上来的问题。合法的做法只有三种：
返回一个能表达「没有答案」的值；打日志、回退，并说清回退成了什么；或者拒绝执行。

「问不出来」和「答案是否」自始至终分开。一个可能答不上来的判定函数，返回类型就不能是裸
`bool`——压成同一个 `false`，调用方只能猜；压成 `true`，那是个安全洞。

日志要能回答「我该做什么」。「subscribe failed」不合格；「这个事件在当前 BDS 版本上不存在，
注册表里相近的有 A、B、C」合格。

### 事件精确解析

只有一个匹配器 `idMatches`，匹配精确 id 或带命名空间分隔符的后缀，**永远不做子串匹配**。
两个松紧不一的匹配器迟早会给出两种答案。

解析顺序，而且认领即负责：

1. 事件提供方认领它。订阅失败就报错，**不**下落到别的路径。
2. 注册表精确名，再唯一后缀。
3. 全部失败则报错，并列出相近的 id。

提供方之所以排在注册表之前：命令事件的发射器**就在**注册表里，但 LeviLamina 只把它派发给
类型化监听器——动态路径查得到、接不到。这类提供方声明自己覆盖注册表路径。纯合成的事件
声明自己不覆盖，一旦上游出现同后缀的 id 就打告警，因为这种遮蔽必须可见。

### 契约只增不减

新增能力就是在表尾追加一个槽，版本号不动。重排、删除或改签名，则 `PIER_ABI_VERSION` 和
`PIER_ABI_MIN_SUPPORTED` 一起推进到同一个数，在那之前编译的模组会在装载时被明确拒绝并说明原因。

兼容是一个区间，不是相等：`MIN_SUPPORTED <= 模组的版本 <= 宿主的版本`。

`tools/abi-v1.slots` 是基线，每次推送都有检查对着它比，所以非追加式的变更没法悄悄落地。

### 每条规矩都有脚本守着

**一条没有脚本守着的规矩等于一句愿望**，而这不是修辞：object 库那条规矩，是在它已经写进契约、
交付说明也宣称它成立之后被违反的，而且恰恰违反在那四个完全依赖自注册的包上。

`python3 tools/run-checks.py` 一次跑齐。它们查的是编译器和 clippy 查不到的东西：
头文件能否按 C11 和 C++20 各编一遍、槽序是否只增不减、Rust 镜像是否逐参数对得上、
能力包之间有没有横边、有没有注释在说代码没做的事。

其中三条的形状值得单独记：它们盯的错误**在编译期完全看不见，装载期才报，
而报出来的话和构建过程毫无关系**。manifest 的 type 写错，模组根本不会被扫到，不报错；
少写内存算子，构建全过，启服时才被拒绝。

每条检查都写明自己覆盖到哪、看不见什么，交付说明只许照抄那句话。脚本通过只等于机械规则成立，
不等于那条性质成立。

规矩本身在 [`CONTRACT.md`](CONTRACT.md) 里，每一条都写了理由。

## 写一个模组

**[Rust](docs/zh/rust/index.md)** 是第一个官方绑定，也是目前该用的那个。

```rust
use levilamina::prelude::*;

struct MyMod;

impl LeviMod for MyMod {
    fn on_load(ctx: &ModContext) -> Result<Self> {
        ctx.logger().info("hello from Rust");
        Ok(MyMod)
    }
}

levilamina::register_mod!(MyMod);
```

- [写你的第一个模组](docs/zh/rust/first-mod.md) 从构建到装上服务器走一遍。
- [pier-mod-template](https://github.com/Maskviva/pier-mod-template) 是一个能跑的起手模板，
  不是空壳。

## 绑定另一门语言

一份文件就够了。`sdk/abi.h` 能被 C11 解析，FFI 工具直接吃；它同时就是参考文档：
每个槽位都写明参数含义、失败时返回什么、对线程有什么要求。

1. 镜像 `PierApi`，**无条件声明每一个字段**，不带任何目标分支。
2. 导出 `pier_main`，往 vtable 里填 `struct_size`、`abi_version`、`mod_flags`
   和三个生命周期回调。
3. 调用任何非核心槽之前，先查 `struct_size` 覆盖得到它，再查槽位非空。

`bindings/rust/pier-sys-rs` 是参考实现。
[加一门语言](docs/zh/guide/adding-a-language.md) 有详细步骤，
[`CONTRACT.md`](CONTRACT.md) 第十节是权威版本。

## 安装

用 [lip](https://lip.futrime.com)：

```bash
lip install github.com/Maskviva/pier
```

或者把发布压缩包解压到 `plugins/pier/`。

Pier 需要 BDS 1.26.20 上的 LeviLamina 26.20.4。
[LegacyMoney](https://github.com/LiteLDev/LegacyMoney) 是可选的：它走延迟加载，
没装的服务器照常启动，只有经济相关的调用返回失败值。

## 从源码构建

```bash
xmake f --target_type=server && xmake   # 宿主本体 pier.dll
cargo build --release                    # Rust 绑定与示例
```

两条构建线之间没有构建依赖，只有那份头文件，所以它们可以分别修。

```bash
python3 tools/run-checks.py   # 契约第九节的机器检查
```
